A full attempt at "pick up the red tape roll"

Both tries stopped on the second request to the model with the error "Invalid RTC delay". The arm then returned to its start position. The next section explains why.

Why it stopped

Each answer from the model is one second of motion. To keep the arm moving, the robot asks for the next answer before the current one runs out, and it guesses how late that answer will be from how long the first answer took. The first answer is slow, so the robot asked the model to skip more steps than one answer contains, and the server refused.

What to try next

Try first

Stop-and-go mode

A small script on Zyad's Mac makes the arm finish each second of motion, wait for the next answer, then continue. Movement will be choppy, but it should get through a full attempt. Written and checked, not yet run on the arm.

Then

Smooth mode

Warm up the model with a realistic request at the start of each session, or stop the robot from trusting the first slow answer. Then the arm can move continuously at the real 0.17 s speed.

Alternative

Any NVIDIA computer next to the arm

If the lab has a Linux machine with an NVIDIA GPU of 16 GB or more, plugging the arm straight into it skips the server and tunnel entirely. LeRobot's normal local mode pauses briefly for each answer, which works fine at 0.17 s.

Good to know

  • Don't recalibrate. If LeRobot asks, press Enter to use the existing file. Typing c writes new settings to the motors, and everyone's calibration file stops matching.
  • Camera numbers can change when anything is replugged or an iPhone connects as a camera. Run lerobot-find-cameras opencv again if the arm acts blind.
  • The stand camera is very wide. The arm takes up a small part of its picture, while the model was trained on closer third-person views. It may do better with tighter framing; let's decide together before moving any camera.
  • When a run ends, the arm goes limp. Hold it if it's raised. Keep a hand near the power during runs.
  • Still unknown: whether MolmoAct2 does the task on our arm, and whether it follows a changed instruction mid-run. The second question decides the VLM-over-VLA plan.
